ダッシュ攻撃の正常化

v11.4.2間隔と、画面の戻り方

ループ再生の待ちを前後に分け、位置を戻したときに画面のスクロールも 一緒に戻るようにしました。

待ちを Before と After に分けました

親の行は Loop Interval (Frames) : (Before/After) です。右か LP で 子メニューが開き、レバーだけで操作できます — 左で減り、右で 増え、上下で行を移り、一番下の Back で戻ります。

  • After は前の周が終わってダミーが動けるようになってから 数える待ちです。今までの Loop Interval と同じ位置なので、 保存していた値は自動で After に引き継がれます。
  • Before は距離を戻したあと、次の周が出るまでの待ちです。

待ちが 1 か所しかないと、「距離を戻す前に間を置く」と「戻してから間を置く」を 区別できませんでした。Reset Distance Each Loop でワープしてから 一拍おきたい、という使い方ができます。

位置を戻すと画面も戻ります

これまでは 2 人の位置は戻っても画面のスクロール位置が戻り切らず、 さらに画面の外に置かれたキャラクターが引き戻されることがありました。ガロンの K 投げのように 2 人が入れ替わって大きく動く録画で特に目立ちました。 録画ウィザードの確認再生、Reset Distance Each Loop、 キャラクターポジションの変更、どれも画面が一緒に動きます。

そのほか

  • メニューを閉じた直後、リピート再生が 30 フレーム止まります。 閉じた瞬間に次の周が飛んでくると構える間がないためです。単発の再生には 影響しません。
  • 保存メニューの Play again は、ダミーが動き終わるまで 選べません。動けないダミーに向けて再生し直しても状況が再現されない ためです。Save と Record again は即座に応答します。
  • 録画ウィザード中は Lua Hotkey 1(中止)だけが効きます。
  • v11.3.x で保存した設定が正しく引き継がれるようになりました。 選んでいたリバーサルが隣の項目にずれることがありました。
  • 複数ヒットするガードのあとでも、リバーサルとカウンターアクションの 必殺技が出るようになりました。
  • Knockdown Logger をオフにしたときに、診断用の記録が 完全に止まるようになりました。オフでも一部が動き続けて動作が重く なっていました。

v11.4.1ウィザードを実際に使って直した分

v11.4 で入れた録画ウィザードを使ってみて出てきた点をまとめて直しました。 ハイジャンプはスーパージャンプに改名しています (並び順とインデックスは変えていないので設定への影響はありません)。

レバーだけで回せます

スロット選択も保存確認も一覧になり、上下で選んで LP か右で決定します。 保存確認は「保存 / 録り直し / 再生し直し」を縦に並べました。 メニューでは右が「奥に進む」操作なので、Play Recording と Recording Wizard にも右で入れます。ボタンの直接操作もそのままです。

保存するとスロット一覧に戻ります。結果を1秒表示してから戻るので、 続けて別のスロットも録れます。戻るときにキャラクターの距離も録画開始時に戻します。 一覧の一番下には Back to menu があり、Lua Hotkey 1 で 中止したときもメニューが開き直します。

Reset Distance Each Loop

ループの各周の頭で、録画したときの距離に戻します。 周を重ねるうちに離れていって、練習していた状況が起きなくなる問題への対処です。 距離は録画ファイル自身に記録されるので、v11.4.1 以降に録ったものが対象になります。

セーブステートまわり

Use Savestate Upon Recording が有効なとき、 読み込みでスクリプトが停止することがありました。 名前付きのステートを読むと、番号付きスロットしか受け付けない処理へ文字列が渡っていたためです。

セーブステートは取った試合の中だけで有効になりました。 キャラクターを選び直すと読み込まれません。

ステートはマシン全体の状態です。1P サスカッチ / 2P デミトリで録って 選び直して逆にすると、設定が戻るのではなく古い試合が丸ごと画面に返ってきます。 保存時に両者のキャラクター ID を控え、読む前に照合しています。 食い違えば読み込みだけを飛ばし、再生自体は続けます (録画データはダミーのキャラ別に分かれているので、そちらは正しいものが読まれています)。

入場演出中の操作

演出の最中に位置のショートカットを使うと配置が壊れて操作不能に見える状態に なっていました。スライドは毎フレーム X を書きますが、演出中はゲーム側も書いているので 両者が奪い合い、キャラは意図しない場所に取り残されてカメラも追随しません。

ラウンドが整うまで Lua Hotkey 1 と 2 を受け付けません。 配置はラウンド開始時の2人の位置から計算するので、その値を読み直すまでは基準がありません。 メニューだけ開けても同じで、演出の途中で両キャラを止めたまま置き去りにするので、位置と一緒に塞いでいます。

再生中は Coin での操作の入れ替えも受け付けません。 再生がダミーを動かしているところへパッドを移すと、両方が同じ側を書いてどちらも正しく動きません。

v11.4 / 01録画ウィザード

ダミーの録画を案内付きで行えるようにしました。 Recording タブの Recording Wizard から始めます。 スロットを選ぶと操作がダミー側に切り替わり、 動かし始めたところから録画が始まります。 手を止めると終わり、そのまま録ったものを一度再生して見せます。

ウィザードの流れ 
スロット選択   録画した日時が出るので、上書き先を選べます
録画開始       最初の入力から。それまで操作は受け付けません
自動終了       技が終わってから 2 秒
確認再生       位置と向きを録ったときの状態に戻してから再生
保存           LP 保存 / MP 録り直し / LK もう一度再生

終了条件は「技が終わってから」です。 レバーがニュートラルなだけでは終わりません。 長い技の途中で録画が切れることがなくなります。

確認再生の前に両キャラを録画開始時の位置に戻します。 録ったときと同じ間合いで再生されるので、 保存する前に、狙った動きになっているかを確かめられます。 気に入らなければその場で録り直せますし、何度でも見直せます。 Lua Hotkey 1 でいつでも中止できます（そのときは保存されません）。

スロットの録画日時は Recording タブの Enable Slot 1〜5 にも出ます。 どれが古い録画かが分かるので、上書きしてよいスロットを選べます。

v11.4 / 02ハイジャンプ

ダミーの行動に 前ハイジャンプ / ハイジャンプ / 後ハイジャンプ を追加しました。 Reversal/Counter Input Motion の一覧、バックダッシュキャンセルの次に並びます。 下を入れてから上に入れる形で、前後は上を入れるときに乗せます。

リリス、モリガン、ガロン（クライムレーザー）のように、 ハイジャンプを経由する行動を練習するための追加です。

一覧の途中に足したので、それ以降の項目の並びが変わります。 設定ファイルは初回起動時に自動で移行されるので、 保存済みの設定はそのままの意味で引き継がれます。 v11.3.1 のときのように選び直す必要はありません。

v11.4 / 03ガード後のバックダッシュ

v11.3.1 で既知の不具合として挙げていたものが直りました。 硬直の長い技ほど失敗しやすく、弱 80% / 中 40% / 強 8% しか出ていませんでした。

ガードさせた技旧v11.4本数
弱80%100%20
中40%100%20
強8%100%17

原因はガードのために後ろを握っていることそのものでした。 タップのために一度レバーを離すと、 「握り → 離す → タップ」がその場でダッシュの成立条件を満たしてしまい、 まだ硬直中なのでその要求が捨てられていました。 一度成立すると認識器はそれ以上受け付けないので、 こちらが本来狙っていた 2 回目のタップは無視されます。

離すときにニュートラルを明示的に入れて認識器を通常の手順で戻し、 そのうえで硬直の強さごとに置く位置を変えるようにしました。 メモリを書き換えて認識器を消す方法も試せましたが、 タイミングはメモリから読み、操作はあくまで入力で行うという このツールの方針から外れるので採っていません。

v11.4 / 04再生まわり

  • Play Recording を追加しました。Recording タブの一番上から、 現在のスロットをそのまま再生できます。再生ホットキーと同じ動作で、 もう一度押すと止まります。
  • 1P と 2P が入れ替わっていても、左右を自動で反転して再生します。 録画は絶対方向のレバー入力なので、逆側に立っていると鏡像の動きになっていました。 録画時にどちら側だったかをファイルに記録し、再生時に見比べています。
  • ループ再生が、ダミーの動ける状態を待ってから次の周を始めます。 これまでは前の技の硬直中に次の周が始まっていたため、 1 周目が出ないことがありました。 セーブステートを使う設定では、従来どおり即座に再開します。
  • キャラクターセレクトに戻った後（Lua Hotkey 4）も 再生状態が続いてしまう問題を直しました。

あわせて直した細かいもの。 録画ウィザードを起動したとき、決定に使ったボタンが ダミーの攻撃として出てしまう問題を直しました。 録画日時の表記を 24 時間制に統一しました。 試合が始まるまでの間、Lua Hotkey 1 と 2 を受け付けないようにしました。

メニューの配色も見直しています。選択中の項目が読みやすくなりました。 Display タブと Etc タブの初期値も見直しましたが、 これは新規インストール時のみ適用されます。既存の設定は変わりません。

v11.3 / 01ボタンを押す瞬間のレバー

Reversal/Counter Button Lever を追加しました。 Motion / Delay / Button に並ぶ入力記述の4段目です。 押しの瞬間のレバーだけを差し替え、モーション側には触れません。

これまでダッシュは方向を握ったままボタンを押していたので、 ダッシュ攻撃しか出せませんでした。 バレッタのダッシュニュートラル中P は出す方法自体がありませんでした。 Neutral がそれを解きます。ザベルのバックジャンプから↓中Kなら Down。

v11.3 / 02プッシュブロックがガードの種類に

Guard に Push Block (All Light / All Medium / All Heavy) が 加わりました。All Guard と同じ守り方をしたうえで押します。

これまでプッシュブロックは Guard Action Type にいたため カウンターと排他で、「プッシュブロックしてから反撃」が組めませんでした。 防御の側へ移したので Guard Action Type が空き、 最速プッシュブロック → ダッシュ攻撃が確定するか を調べられます。

プッシュブロックが成立すると、ゲームはガード硬直とは別の時計に 切り替わります。そちらでも最速行動が出ます。 成立した時点で残りの連打は捨てるので、後続の行動がすぐ入ります。

v11.2 / 01立ち位置の設定

Player タブの一番上に Position を追加しました。 言葉ではなく図で選びます。1 が自分、2 がダミー、 | が壁です。レバーの左右がそのままステージ上の左右に対応します。

6 通り 
|12------|   自分が左端
|21------|   相手が左端
|---12---|   中央(開幕の位置)、自分が左
|---21---|   中央(開幕の位置)、自分が右
|------12|   相手が右端
|------21|   自分が右端

端の 4 つは壁に密着します。間隔はこちらで決めず、 立てないほど近い位置に置いてゲーム自身の押し合いに任せます。 キャラの体格差に関係なく正確な密着になります。

中央の 2 つはラウンド開始そのものの位置と間隔です。 ゲームがラウンド開始時に置いた位置を毎回読み取って使うので、 開幕に何が届くかの練習にそのまま使えます。

レバーだけで呼び出せます

メニューを開かなくても、Lua Hotkey 2 とレバーの組み合わせで切り替えられます。 覚える規則は一つ、「下 ＝ 特別な側が自分」。 端なら自分が壁側、中央なら自分が 2P 側です。

←        相手が左端        |21------|
↓ ＋ ←   自分が左端        |12------|
(なし)   中央 自分が 1P 側  |---12---|

移動中の約 1 秒はレバーもボタンも効きません。 配置を選ぶために倒したレバーがそのままキャラを歩かせてしまうためで、 Start と Coin は落としていません(ポーズと操作側の切り替えは残ります)。

直接その座標に置く方式はやめました。座標を書いても 画面のスクロールが付いてこないので、キャラだけが画面端に 引き戻されて、狙った位置に立ちません。

てくてく歩かせています。毎フレーム少しずつ動かせば、普通に歩いた のと同じ状況になり、カメラは自分で追いつきます。端から端まで約 1 秒です。 移動中の約 1 秒はレバーもボタンも効きません(配置を選ぶために倒したレバーが そのままキャラを歩かせてしまうため)。

ステージの端は全ステージ共通でした。 2 ステージを実測して左 280 / 右 1000。開幕位置は 554 / 728 で、 その中点 641 は壁から出る中央 640 と一致します。 独立した 2 つの測定が揃ったので、ステージ別の表は要りません。

v11 / 01ガード後の最速行動

v10 の時点で、ガード後の最速行動は技によって出たり出なかったりしていました。 原因を追ったところ、ガード硬直の仕組みそのものを取り違えていたことが分かりました。

ガード硬直にカウンタは存在しません

硬直の残り時間を数えている変数はありません。 ゲームは技ごとに決まった押し戻しスクリプトを 1 ティック 1 バイトずつ歩き、 バイトが尽きたところで硬直が明けます。バイトの値はそのティックの押し戻し量そのものです。

硬直の長さと押し戻しの距離は、同じデータです。 弱 11 ティック / 中 16 / 強 20。プレイヤーのメモリを全部走査してもカウンタが見つからなかったのは、 最初から存在しなかったからでした。

時計を間違えていました

旧方式は別のカウンタ ($158) を時計に使っていました。これは ヒットストップ中も減り続けますが、押し戻しスクリプトのほうは止まります。 つまり両者は止まりの長さちょうどぶんだけズレます。

デミトリのゼロデモンのように止まりが長い技では、スクリプトが 1 歩も進まないうちに 旧時計が燃え尽きてしまい、狙った時刻が硬直明けを追い越していました。

強攻撃のガード 229 本旧方式v11
狙いが硬直明けの手前に来た 118 221
硬直明け以降に落ちた（＝何も出ない） 111 8

ゼロデモンのガード硬直は 20 ティックで、普通の強攻撃と同じでした。 硬直が短かったのではなく、こちらが見ていた時計だけが先に進んでいた、というのが答えです。

スクリプトはガードが成立した時点で全部読めるので、 硬直の残りがガード 1 ティック目で確定値として分かります。 強さごとの当て推量を実測値に置き換えました。

v11 / 02オートガード（All Guard / Stand Block）

後ろを入れたときにガードポーズを取って動けなくなるかどうかは、 ゲーム自身が判定を持っています。仕様はこうです。

  • 飛び道具は画面上のどこにいても効きます（距離を見ません）
  • 通常技・必殺技は技ごとに距離が決まっていて、その外では後ろを入れても歩くだけです

従来の実装が見ていたのは「相手が攻撃モーションに入った」と「一定距離以内」の 2 つだけで、 これはゲームのルーチンの最後にある粗い保険だけを抜き出した形でした。 そのため次の 2 つが起きていました。

症状原因
飛び道具や別オブジェクトの技を見ない 相手プレイヤーの攻撃フラグしか見ておらず、オブジェクトを走査していなかった
届かない技の空振りでも後ろに下がる 技ごとの判定枠データを見ておらず、届くかどうかを判断していなかった

v11 ではゲームの判定をそのまま移植しました。オブジェクト走査（飛び道具を距離に関係なく拾う）と、 技ごとの判定枠テーブル（届くかどうかを技のアニメーションから先読みする）の両方が入っています。 持続の長いデモンクレイドルを空振りしても下がりません。

正しい距離判定が入ったことで、後ろは押しっぱなしで構わなくなりました。 判定が真＝ゲームがガードポーズを認める＝後ろを入れても歩かない、という関係だからです。 これまで一瞬だけ押していたのは、間合いの中かどうかを判断できなかったための回避策でした。

v10入力を「ティック」で置くようになりました

これまでダミーの入力は表示フレーム単位で出していました。 ゲームが実際に入力を読む単位はティックで、この二つは一致しません。 そこがずれている限り「最速の行動」は原理的に出せませんでした。そこを作り直したのがこの版です。

DPF でリバーサルが出るようになったのはここからです。 以下はその作り直しの中身で、今の版の土台にあたります。

v10 / 土台ティックと表示フレームは別物です

ターボ3 では 3 表示フレーム = 4 ティックです。 攻略 wiki が「ターボ3 = ノーマル × 0.75」と書いているのと同じことを、逆から言っています。

ゲームは1 ティックごとに入力を読みます。ところが Lua から見える joypad.set は表示フレームに 1 回しか回りません。つまり従来の作りは ゲームが入力を読むティックの約 4 割を、そもそも見ていませんでした。

これが「あと 1F 早く出したいのに出せない」の正体です。狙ったティックに入力を置く手段が無く、 表示フレームの刻みに丸められていたわけです。3 エントリのコマンドを 3〜5 ティックの間に 通そうとすると、真ん中の斜めが 1 フレームももらえずに消える ― 斜めの無い波動コマンドは波動コマンドではありません。

そのため画面とメニューの表記も全部 Tick に統一しました。 これまで「frames」と書いてあった数値の多くは表示フレーム数で、ゲームの内部時間とは違うものでした。 嘘の単位が残っていると調整のたびに迷うので、実体に合わせて書き直してあります。 いまも表示フレーム基準のままの表示(ダッシュ間隔・ダッシュ時間などのトレーナー)は、 説明文に「DISPLAYED frames — not game Ticks」と明記しました。

中核入力の書き込み方を変えました

ゲームが入力を読み込む直前の一点(0x02211A)にフックを置き、 そこでメモリへ直接書くようにしました。ここは 1 ティックに 1 回必ず通るので、 狙ったティックに、狙った入力を、確実に 1 つ置けます。

これで初めて「ゲームと同じ時間軸で入力を組み立てる」ことができるようになりました。 以下はすべてこの上に乗っています。

押した瞬間と行動の関係

実測 373 スパンで例外なし ― ティック X で押しのエッジが立つと、行動はティック X+1 に出ます。 「押した」と「出た」は必ず 1 ティックずれます。

動ける最初のティックを特定する

やられ・ガード・ダウンから復帰する 1 ティック前に、ゲームが必ず書き込む署名があります (move.l #$2020400,($4,A6))。ここを捕まえると 「次のティックでこのキャラは動ける」と確定できます。14 キャラ中 13 キャラで 250 回中 249 回。残る Q-Bee だけは別経路なので個別に処理しています。

実装が従う規則

必殺技コマンドで出すもの以外は、すべて free+0。

押しが free+0 に乗らなければ出ません。遅れて出るのではなく、出ません。 1 ティック外しただけで、ダッシュは通常技に化けます。 必殺技コマンド(波動・昇龍・半回転・1 回転など)だけが free−1 で、 それ以外(ダッシュ・ダッシュ中断・通常技・投げ・ジャンプ・DF)は全部 free+0 です。

プレイヤーには当たり前の話です。これまでのトレーニングモードが それを守れていなかったのは、表示フレーム単位では free+0 という 1 ティックを 指せなかったからで、今回ようやく実装が同じ土俵に乗りました。

ダッシュが成立する条件 
free-2   前         1 回目のタップ
free-1   (中立)     押しエッジを作るための解放
free+0   前         2 回目のタップ  ← 1 ティック外すと出ない
free+1   前         ダッシュ成立

free+0 が free+1 にずれるだけで、ダッシュは遅れて出るのではなく 存在しなくなり、代わりに通常技が出ます。この規則を知らずに 5 回作り直しました。

売り 01最速行動

署名から数えて置くようになったので、リバーサルもカウンターも キャラが動ける最初のティックちょうどに出ます。

条件最速で出た何も出ない
全エントリが届き、ボタンが free−1 30 0
それ以外 0 50

間の状態がありません。「だいたい合っている」は存在せず、合っているか出ないかのどちらかです。 だから「たまに出る」を「精度が甘い」と読んではいけない、というのが今回いちばん時間を使った学びでした。

カウンター機能もリバーサルと同じ機構に載せ替えました。発火するのは ガード後と地上くらい後だけで、起き上がりと空中やられ復帰では出ません (実測 30/31、起き上がり・空中では一度も発火せず)。

最速で出たかどうかが画面に出ます

行動が出た瞬間、それが最速だったかを画面右に表示します。 最速なら Fastest、遅れたぶんは +3 Tick のように出ます。 「たぶん最速だと思う」を確かめる手間が要りません。

画面右の表示 
Fastest          最速で出た
Special          何が出たか

+3 Tick          3 ティック遅れた
Normal           出たのは通常技だった

2 行目に実際に出た行動の種別を併記しています。 必殺技を狙って通常技が漏れたときに、Fastest だけを見て 「狙い通り出た」と誤読しないためです。 最速の基準は行動の種類で違う(必殺技は free+0、それ以外は free+1)ので、 その差は表示側で吸収しています。

売り 02投げ

Reversal/Counter Input Motion に Forward / Back / Down を追加しました。 起き上がりリバーサル投げ、ガード後のカウンター投げが選べます。

投げは 1F の方向入力とボタンの同時押しなので、ティック精度が無いと「投げに化けない」が起きます。 今回の土台があって初めて成立する機能です。

売り 03ダッシュ攻撃の正常化

これまではダッシュの入力とボタンが同じタイミングで出ていました。 「ダッシュ」と「攻撃」が分かれていないので、当然 「ダッシュしてから攻撃」という形になりません。 ダッシュ攻撃を設定したつもりでも、実際には別のものが出ていた状態です。

今回はダッシュを最速で出し、そこから指定したティック数だけ待ってボタンを押す という形に作り直しました。ダッシュは動ける最初のティックちょうどに出て、 攻撃はその後ろに置かれます。順番と間隔が、設定した通りになります。

前ダッシュ攻撃(モリガン、Auto = 14) 
free+0    前              ダッシュの 2 回目のタップ
free+1    前              ダッシュ成立
  …       前              押しっぱなしで走りを維持
free+14   前 + ボタン     ダッシュ攻撃

間隔は Guard Action Delay (Ticks) で指定します。 Auto はキャラごとの実測値を入れますが、 いま実測で確かめてあるのはサスカッチとモリガンだけです。 残りは旧版から引き継いだ暫定値なので、合わないキャラは手動値でお使いください。

4 方向とも出るようになりました

前ダッシュ・後ダッシュ・前ダッシュ中断・後ダッシュ中断が、 ガードさせた技の強さ(弱・中・強)を問わず安定して出ます。 そもそもダッシュが出なければ攻撃も載せられないので、こちらも合わせて直しています。

後ろダッシュが出なかった理由

ダミーはガードのためにレバーを後ろに握りっぱなしです。 そこへ「後ろ」をもう一度入れても、ゲームから見れば何も変わっていないので 押しエッジが立たず、1 回目のタップが存在しません。

そこで一度レバーを離してから押し直すようにしました。 離す長さ・タップを持つ長さ・置く位置の 3 つを調整できるようにしてあります。 前ダッシュは握っていないので、この処理は後ろ側にだけ効きます。

後ダッシュ(ガード中) 
free-8 … free-5   (中立)      握っていた後ろを離す
free-4 … free-3   後          1 回目のタップ(2 ティック保持)
free-1            (中立)
free+0            後          2 回目のタップ
free+1            後          ダッシュ成立

ダッシュ中断

中断の入力そのものは平ダッシュと同一で、ダッシュが立った後に逆方向へ倒して、そのまま保持します。 攻略 wiki が「認識するタイミングは 1F のみだが、ダッシュした直後から入れっぱなしで問題ない」と 書いている通りで、握ってしまえば 1F の窓は外しようがありません。

デミトリだけはダッシュ中断そのものが存在しません(wiki 基本動作「中断不可」)。 設定はできますが出ないのが正しい挙動です。

Guard Action Delay に Auto が入りました

ダッシュを選んだときだけ Auto が選べます。 キャラごとのダッシュ攻撃タイミングが自動で入るので、数値を覚える必要がありません。 左右キーでいつでも手動値(0〜50 ティック)に移せます。

これは v10 時点の話です。当時はサスカッチとモリガンだけが実測済みで、 他キャラは旧ビルドから引き継いだ暫定値でした。 v11.3 で全キャラ実測に置き換わっています — 上の v11.3 の節をご覧ください。

その他あわせて直したもの

プッシュブロック

ゲームはブロック開始時に開く約 12 ティックの窓の中で、押した回数を数えています。 従来は 11 個の入力を表示フレームに 1 つずつ出していたので約 18 ティックかかり、 後半のタップが窓の外に落ちていました。ティック単位に変え、 6 回すべてが窓に入るようになりました(実測 32/32、成立 88/90)。

Minimum PB Inputs が両プレイヤーに効いていた不具合も直しました。 ダミー相手の練習のつもりで上げると、自分のプッシュブロックも同じだけ厳しくなっていました。 Show Pushblock Counter は、ダミーがプッシュブロック設定のときに ダミー側の回数も表示します(6 以上で緑)。

フレームトラップ表示

Frame Gap は表示フレーム差だったので、3 ティックの隙も 4 ティックの隙も同じ「2」と出ていました。 ティックで測るようにし、表示も Tick Gap に変えています。

クラッシュ修正

Use Random Recording Slot が ON で Enable Slot 1〜5 が全部 OFF のとき ―― このオプションの初期状態そのものです ―― 録画再生を伴うガードアクションで スクリプトが停止していました。

撤去した機能

True Reversal を削除しました。joypad で制御しきれない中で最速を狙うための機能でしたが、 別の時計で最速が出せるようになったので役目を終えています。

既知の制限まだ手が入っていないところ

  • ダッシュ間隔 / ダッシュ時間 / ダッシュ攻撃キャンセル / 攻撃ダッシュ間隔 / Jump In のトレーナーは表示フレームのままです。説明文にその旨を明記しています。
  • Jump In Trainer に既知の不具合があります。当てずに着地しただけでも、前回の飛び込みとの差が記録されることがあります。
  • 録画型のカウンター(Counter Attack - Recording / PB Recording)はマクロ再生の性質上、フレーム単位のままです。
  • オートガードの後ろ入力は表示フレーム単位ですが、これは意図的です。必要なのは押しの精度ではなく、飛んでくるものが到着したときにまだ押していることなので、ティック化は不要でした。
  • 録画ウィザードにセーブステートは付いていません。確認再生は位置と向きを戻して行いますが、体力やゲージまでは戻りません。
  • run-ahead には未対応です。有効なままだと最速行動が安定しないため、検出して画面で警告します。トレーニング中は切ってください。

v11.4.2The gap, and how the view comes back

The wait between loop passes is now two settings, and putting the pair back brings the scrolling with it.

Before and After

The parent row reads Loop Interval (Frames) : (Before/After). Right or LP opens a child menu you can work entirely with the stick - Left lowers, Right raises, Up and Down change row, and Back at the bottom returns.

  • After is counted once the previous pass has ended and the dummy can act again. That is where the old Loop Interval sat, so a saved value carries over to After on its own.
  • Before is counted after the distance is restored, just before the next pass goes out.

With only one wait there was no way to tell "pause before putting them back" from "pause after putting them back". Now you can have a beat after Reset Distance Each Loop warps the two into place.

The framing comes back too

The two characters went back but the scrolling did not, and a character placed outside the old view could be dragged back into it. It showed up worst on recordings that moved a long way with the sides swapped, such as Gallon's kick throw. The wizard's check playback, Reset Distance Each Loop and the character position shortcut all bring the view with them now.

Also

  • Looped playback holds for 30 frames after you close the menu, so the next pass does not arrive the instant you leave it. Single playbacks are unaffected.
  • Play again cannot be taken until the dummy has finished moving - replaying against a dummy that cannot act reproduces nothing. Save and Record again answer immediately.
  • Only Lua Hotkey 1 (cancel) works while the recording wizard is up.
  • Settings saved by v11.3.x now carry over properly - the chosen reversal could end up one entry off.
  • Reversals and counter-action specials now come out after a multi-hit guard.
  • Turning Knockdown Logger off now stops the diagnostic recording completely - part of it kept running with the setting off and slowed the game down.

v11.4.1What using the wizard turned up

Everything that came out of actually using the Recording Wizard added in v11.4. High Jump is renamed Super Jump (the order and the indices are unchanged, so settings are unaffected).

The stick alone drives it

Slot selection and the save prompt are both lists now: up and down to move, LP or Right to take it. The save prompt reads Save / Record again / Play again down the screen. Right is how you go into things elsewhere in the menu, so Play Recording and Recording Wizard take it as well. The buttons still work as direct shortcuts.

Saving returns you to the slot list. The result stays up for a second first, so the next slot can be recorded straight away, and the characters go back to the distance the take started from as the list comes back. Back to menu sits at the bottom of the list, and cancelling with Lua Hotkey 1 reopens the menu too.

Reset Distance Each Loop

Puts both characters back to the distance the recording was made from at the start of every loop. Without it the two drift apart over the passes and the setup you were practising stops happening. The distance is stored in the recording itself, so this works on takes made from v11.4.1 on.

Savestates

With Use Savestate Upon Recording on, a load could halt the script. Loading a named state handed a string to something that only takes a numbered slot.

Savestates are now only valid inside the match they were taken in. Reselect the characters and the state is not loaded.

A state is the whole machine. Record with P1 Sasquatch and P2 Demitri, reselect the two the other way round, and a playback did not restore a setup - it dragged the old match back onto the screen entire. Both characters' ids are noted alongside the state and checked before every load. A mismatch skips the load only and the playback still runs, because the recordings are already kept per dummy character.

During the entrance

Using the position shortcut while the characters were making their entrance shredded the arrangement and read as dead controls. A slide writes X every frame and so does the game during the entrance; the two fight, the pair is left somewhere neither intended and the camera never follows.

Lua Hotkey 1 and 2 are ignored until the round is under way. Every arrangement is computed from where the two stood at the round start, so until that has been read back there is no basis to work from. Allowing just the menu is no better - it leaves both characters disabled partway through the intro - so the two are held back together.

Coin no longer swaps control while a playback is running either. Moving the pad to the dummy while the playback is driving it means both are writing the same side and neither comes out cleanly.

v11.4 / 01Recording Wizard

Guided dummy recording. Start it from Recording Wizard on the Recording tab. Pick a slot and control switches to the dummy; recording begins the moment you move. Stop moving and it ends, then plays the take back once so you can look at it.

The wizard, step by step

Auto-stop       two seconds after the move finishes

v11.4 / 02Super Jump

Super Jump Forward / Super Jump / Super Jump Back are now dummy actions. They sit in Reversal/Counter Input Motion, after Back Dash Cancel. Down, then up - with the direction on the up.

Added for the actions that go through a super jump, on Lilith, Morrigan and Gallon (Crime Laser).

They were inserted into the middle of the list, so everything after them shifts. The settings file migrates itself on first launch, and a saved setting keeps its meaning. There is nothing to re-pick, unlike v11.3.1.

v11.4 / 03Guard cancel back dash

The known issue listed in v11.3.1 is fixed. The longer the blockstun, the more often it failed - 80% on light, 40% on medium, 8% on heavy.

Light80%100%20
Medium40%100%20

The cause was holding back to block in the first place. Releasing the stick to make the tap meant "hold, release, tap" satisfied the dash on the spot - still inside blockstun, so the request was thrown away. The release now puts an explicit neutral in to walk the recogniser back the ordinary way, and where the taps are placed varies by the strength of the blockstun. Writing to memory to clear the recogniser would have worked too, but timing is read from memory while the input is performed as input in this tool, and that is not the way to keep it.

v11.4 / 04Playback

  • Play Recording plays the current slot straight from the top of the Recording tab. Same as the playback hotkey; press it again to stop.
  • Playback is mirrored when P1 and P2 have swapped sides. A recording is absolute stick directions, so from the other side it used to come out as its mirror image. Which side the take was recorded from is stored with it and compared on playback.
  • Looped playback waits for the dummy to be able to act before the next pass. The first input used to land during the previous pass's recovery, where it simply would not come out. With a savestate in play it restarts as before.
  • Playback continuing after a return to character select (Lua Hotkey 4) is fixed.

Smaller things. The button that confirms a slot in the wizard no longer reaches the game as an attack. Recording times are shown on a 24-hour clock. Lua Hotkey 1 and 2 are ignored until the round is under way.

The menu palette has been reworked; the selected row is easier to read. The Display and Etc tabs have new defaults, which apply to a fresh install only and leave an existing settings file alone.

v11.3.1Fixes

  • Push block was being dragged around by the delay setting. With Guard Action Delay on anything but Auto, that many empty frames went in ahead of the taps, pushing them out of the game's 12-tick window - so no push block came out. A delay does not apply to how you defend.
  • No back dash after a push block. A successful push block switches the game to a different clock, but the taps were still being placed against the old one and never landed inside the window.
  • Auto values re-measured. Morrigan 12 / 13, Jedah 10 / 9 (forward and forward cancel; back is the same).
  • Dash ordering fixed so forward comes before back. A saved setting shifts by one, once, so re-pick Reversal/Counter Input Motion.
  • The Auto description now says the values were measured for the fastest action after a block, and that after a hit they are sometimes not enough (Morrigan and Jedah especially).

v11.3 / 01The stick at the moment of the press

Reversal/Counter Button Lever is new: a fourth stage of the input description alongside Motion, Delay and Button. It replaces only the stick at the instant of the press and leaves the motion alone.

A dash used to press the button while still holding the direction, so a dash attack was all you could get. Bulleta's dash neutral MP had no way to be performed at all. Neutral unlocks it. Zabel's back jump into down MK wants Down.

Forward and back are resolved against the facing at the moment of the press, so the list does not grow for the right-hand side. The default As Is behaves exactly as before.

v11.3 / 02Push block as a way of blocking

Guard now offers Push Block (All Light / All Medium / All Heavy). It defends the way All Guard does, and pushes on top of that.

Push block used to live under Guard Action Type, which made it exclusive with counters - there was no way to ask for "push block, then hit back". Moving it to the defensive side frees Guard Action Type, so you can find out whether a fastest push block into a dash attack is guaranteed.

A successful push block switches the game to a different clock from blockstun, and the fastest action comes out on that one too. The remaining taps are dropped the moment it succeeds, so what follows goes in straight away.

v11.2 / 01Where the two stand

Position is at the top of the Player tab. You pick from a diagram rather than from words. 1 is you, 2 is the dummy, | is a wall. Left and right on the stick are left and right on the stage.

six arrangements 
|12------|   you in the left corner
|21------|   them in the left corner
|---12---|   centre (the round start), you on the left
|---21---|   centre (the round start), you on the right
|------12|   them in the right corner
|------21|   you in the right corner

The four corner arrangements put the pair flush against the wall. The gap is not decided here: they are placed closer than any pair can stand and the game's own push-apart sets the real distance. That is exact whatever the two characters' sizes.

The two centre arrangements are the round start's own positions and gap. Where the game put them at the start of the round is read back each time, so practising what reaches on the opening works directly.

The stick alone can call them up

Lua Hotkey 2 plus a direction switches arrangement without opening the menu. There is one rule to remember: "down means the special side is yours". In a corner that is the wall side; in the centre it is the 2P side.

Hotkey 2 + 
left          them in the left corner    |21------|
down + left   you in the left corner     |12------|
(nothing)     centre, you on the 1P side |---12---|
down          centre, you on the 2P side |---21---|
right         them in the right corner   |------12|
down + right  you in the right corner    |------21|

For the second or so that the slide runs neither the stick nor the buttons reach the game. The direction you leaned on to choose an arrangement would otherwise walk your character. Start and Coin are left alone - pause and the control swap still work.

Writing the coordinates directly was abandoned. Writing a position does not bring the screen's scrolling with it, so the character alone is dragged to the edge of the view and never ends up where you asked.

They are walked there instead. Moved a little each frame, the situation is the same as having walked, and the camera keeps up on its own. End to end takes about a second.

The stage edges are the same on every stage. Two stages measured: left 280, right 1000. The round start is 554 / 728, whose midpoint of 641 agrees with the 640 that falls out of the walls. Two independent measurements line up, so no per-stage table is needed.

v11.2 / 02The push block counter

The number being shown was "how many it took", not "how many you pressed". The game's own counter stops the instant it succeeds.

Old displayPresses actually madeCases
3622
4628
5630
6640

120 of 132 were six presses. Six always succeeds, so what you want to see while practising is how many you pressed. That is what is counted now. This is why a 6 never appeared on screen before.

Whether it succeeded is shown by colour. The old rule was "green at 6 or more", but 81 of 90 successes (90%) succeed below 6, so a success was almost never green. The game's own success flag is read instead.

When it is read was wrong too. The old version read once per displayed frame, and the end-of-block handler clears the counter and the window together, so blocking a light attack always read 0. It is now read at the instruction where the game does the counting.

v11 / 01The fastest action after a block

As of v10 the fastest action after a block came out against some attacks and not others. Following it up showed that how blockstun works had been misunderstood outright.

There is no blockstun counter

No variable counts the stun down. The game walks a pushback script chosen per attack, one byte per tick, and the stun ends when the bytes run out. Each byte's value is that tick's pushback.

The length of the stun and the distance of the pushback are the same data. Light 11 ticks, medium 16, heavy 20. Scanning the whole of a player's memory found no counter because there was never one there.

The clock was wrong

The old method used a different counter ($158) as its clock. That one keeps counting during hitstop while the pushback script stops - so the two drift apart by exactly the length of the stop.

Against something with a long stop, like Demitri's Demon Cradle, the old clock burned out before the script had taken a single step, and the moment it aimed at was already past the end of the stun.

229 heavy attacks blockedOldv11
Aim landed before the stun ended 118 221
Landed at or after the end (nothing comes out) 111 8

Demon Cradle's blockstun is 20 ticks, the same as any other heavy. The stun was not short; only the clock we were reading had run ahead.

The script can be read in full the moment the block registers, so the remaining stun is known as a fixed number on the first tick of blocking. Guesswork per strength was replaced with the measured value.

v11 / 02Auto guard (All Guard / Stand Block)

Whether holding back takes a blocking pose and locks the character in place is a decision the game itself makes. The rules are these.

  • Projectiles count from anywhere on screen (distance is not consulted)
  • Normals and specials have a distance per move, and outside it holding back only walks

The old implementation looked at two things - "the opponent entered an attack animation" and "within a fixed distance" - which was only the coarse fallback at the end of the game's own routine. Two things followed from that.

SymptomCause
Projectiles and other objects' attacks not seen Only the opposing player's attack flag was read; objects were never swept
Backing off from a whiff that could never reach The per-move hitbox data was not read, so reach was never judged

v11 ports the game's own decision across. Both the object sweep (picking up projectiles whatever the distance) and the per-move hitbox table (reading ahead from the attack's animation to see whether it reaches) are in. A whiffed Demon Cradle, long as it is, no longer makes the dummy back off.

With the distance judged properly, back can simply be held. The judgement being true means the game grants the blocking pose, which means holding back does not walk. Tapping it briefly was a workaround for not being able to tell whether the attack was in range.

v10Placing input on ticks

Until this version the dummy's input was issued in displayed frames. The unit the game actually reads input on is the tick, and the two do not line up. While that was out of step, "the fastest action" could not be produced even in principle. This is the version that rebuilt it.

This is where DPF reversals started coming out. What follows is what that rebuild consists of, and it is the foundation the current version stands on.

v10 / foundationTicks and displayed frames are different things

On turbo 3, 3 displayed frames = 4 ticks. It is the same statement the wiki makes as "turbo 3 = normal x 0.75", from the other side.

The game reads input every tick. What Lua can reach, joypad.set, comes round once per displayed frame. So the old approach never saw about 40% of the ticks the game reads input on.

That is what "I want it one frame earlier and cannot" really was. There was no way to place input on a chosen tick; it was rounded to the displayed-frame grid. Push a three-entry command through three to five ticks and the diagonal in the middle gets no frame at all - and a fireball motion without the diagonal is not a fireball motion.

The screen and the menu now say Tick throughout. Most of the numbers that used to read "frames" were displayed frames, which are not the game's own time. A false unit makes every adjustment a guess, so they were rewritten to match what they are. The readouts still counted in displayed frames (the dash interval and dash time trainers) say so: "DISPLAYED frames - not game Ticks".

v10 / coreHow input is written

A hook sits at the single point just before the game reads input (0x02211A) and writes straight to memory there. That point is passed exactly once per tick, so one chosen input can be placed on one chosen tick, reliably.

Only then can input be assembled on the same timebase as the game. Everything below rests on it.

The press and the action

373 measured spans, no exceptions - a press edge on tick X produces the action on tick X+1. "Pressed" and "came out" are always one tick apart.

Finding the first actionable tick

One tick before recovering from a hit, a block or a knockdown, the game always writes a signature (move.l #$2020400,($4,A6)). Catching it establishes "this character can act on the next tick". 13 of 14 characters, 249 of 250 times. Q-Bee alone takes another route and is handled separately.

the rule the implementation follows

Everything except a special-move command is free+0.

If the press does not land on free+0 it does not come out. Not late - it does not come out. One tick off and a dash turns into a normal. Only special-move commands (fireball, dragon punch, half-circle, full-circle) are free-1; everything else (dashes, dash cancels, normals, throws, jumps, Dark Force) is free+0.

To a player this is obvious. Training modes had not held to it because a displayed frame cannot point at the single tick that is free+0. The implementation has only now caught up with the player.

what a dash needs 
free-2   forward     first tap
free-1   (neutral)   released so there is an edge to make
free+0   forward     second tap  one tick off and nothing comes out
free+1   forward     dash

Move free+0 to free+1 and the dash does not arrive late, it ceases to exist - a normal comes out instead. Not knowing this rule cost five rebuilds.

v10 / 01Fastest actions

Counted from the signature, reversals and counters come out on the exact first tick the character can act.

ConditionCame out fastestNothing came out
Every entry arrived, button on free-1 30 0
Anything else 0 50

There is no state in between. "Roughly right" does not exist: it is either right or nothing. Which is why "it comes out sometimes" must not be read as "the precision is a little loose" - the longest lesson of this work.

Counters were moved onto the same machinery as reversals. They fire after a block and after a grounded knockdown only, never on wake-up or an air recovery (30/31 measured; never once on wake-up or in the air).

Whether it was the fastest is on screen

The moment an action comes out, whether it was the fastest is shown on the right of the screen. Fastest if it was, or how late it was as +3 Tick. No need to check whether you think it was the fastest.

right of the screen 
Fastest          came out fastest
Special          what came out

+3 Tick          three ticks late
Normal           what came out was a normal

The second line names the kind of action that actually came out, so that a normal leaking out where a special was aimed for is not read as "it worked" from the Fastest alone. What counts as fastest differs by kind (a special is free+0, everything else free+1), and the display absorbs that difference.

v10 / 02Throws

Forward / Back / Down were added to Reversal/Counter Input Motion. Wake-up reversal throws and post-block counter throws can be asked for.

A throw is a one-frame direction and a button together, so without tick precision you get "it did not turn into a throw". It only works on the foundation above.

v10 / 03Dash attacks, properly

The dash input and the button used to go out at the same moment. "Dash" and "attack" were not separated, so of course it never took the shape of "dash, then attack". Setting a dash attack got you something else entirely.

It was rebuilt as put the dash out at the fastest, then wait the given number of ticks and press. The dash comes out on the exact first actionable tick and the attack is placed behind it. The order and the gap are what you set.

forward dash attack (Morrigan, Auto = 14) 
free+0    forward           the dash's second tap
free+1    forward           dash
  ...     forward           held, to keep running
free+14   forward + button  dash attack

The gap is set with Guard Action Delay (Ticks). Auto fills in the per-character measured value. (At v10 only Sasquatch and Morrigan were measured; v11.3 replaced every character with a measured value - see the v11.3 section above.)

All four directions come out

Forward dash, back dash, forward dash cancel and back dash cancel come out reliably whatever the strength of the attack blocked. An attack cannot be put on a dash that never happened, so this had to be fixed alongside.

Why the back dash did not come out

The dummy holds back to block. Feeding it "back" again changes nothing from the game's point of view, so no press edge forms and the first tap does not exist.

The stick is now released and pressed again. How long it is released, how long the tap is held and where it sits are all adjustable. A forward dash is not being held, so this applies to the back side only.

back dash while blocking 
free-8 ... free-5   (neutral)   release the held back
free-4 ... free-3   back        first tap (held two ticks)
free-1              (neutral)
free+0              back        second tap
free+1              back        dash

Dash cancels

The input is identical to a plain dash; after the dash is out, the opposite direction goes in and is held. The wiki puts it as "the window is only 1F but holding it from immediately after the dash is fine" - hold it and the one-frame window cannot be missed.

Demitri alone has no dash cancel (wiki: cannot be cancelled). It can be set, and not coming out is the correct behaviour.

v10 / otherFixed alongside

Push block

The game counts how many presses land inside a window of about 12 ticks opened when the block starts. The old version issued 11 inputs one per displayed frame, which took about 18 ticks, and the later taps fell outside the window. On ticks, all six land inside it (32/32 measured, 88/90 successful).

Minimum PB Inputs applying to both players is fixed as well. Raising it to practise against the dummy made your own push block just as strict. Show Pushblock Counter also shows the dummy's count when the dummy is set to push block (green at 6 or more).

Frame trap readout

Frame Gap was a displayed-frame difference, so a 3-tick gap and a 4-tick gap both read "2". It is measured in ticks and shown as Tick Gap.

Crash

With Use Random Recording Slot on and Enable Slot 1-5 all off - which is this option's own initial state - a guard action involving playback stopped the script.

Removed

True Reversal is gone. It existed to chase the fastest action while joypad could not be controlled finely enough, and a different clock does that now.

Known limitationsNot touched yet

  • The Dash Interval / Dash Time / Dash Attack Cancel / Attack Dash Gap / Jump In trainers still count displayed frames, and say so in their descriptions.
  • Jump In Trainer has a bug: landing without hitting anything can still record a gap against the previous jump-in.
  • Recording-based counters (Counter Attack - Recording / PB Recording) remain frame-based, which is how macro playback works.
  • Auto guard's back input is in displayed frames deliberately. What matters is not the precision of the press but that it is still held when the thing arrives, so ticks were not needed.
  • The Recording Wizard does not capture a savestate. The check playback restores position and facing, but not health or meter.
  • Run-ahead is not supported. It stops the fastest actions being reliable, so it is detected and warned about on screen. Turn it off while training.
